# Good Outside artifact edition

Builds the planner as a self-contained Claude Artifact page. Published copy: https://claude.ai/artifact/Y9tiYMi7tbGVhCN2zkd798 (sharing is set from the page's Share menu).

```sh
cd apps/good-outside/artifact
npm ci
NODE_USE_ENV_PROXY=1 node fetch-data.mjs      # pinned Natural Earth layers into .cache/ (prefix only behind a proxy)
NODE_USE_ENV_PROXY=1 node fetch-terrain.mjs   # elevation tiles for the hillshade, checked against terrain-tiles.json
npm test        # bridge, place search, label placement and catalog tiles
npm run build   # writes dist/ and dist/files.json (published path -> source, content type)
```

The build also bundles the provider catalog when `../data/openbeta.json`, `../data/openskidata.json` and `../data/ridb.json` exist (from `npm run data:download` at the repo root, or the release files checked against `data/snapshots.json` and unzipped there). Without them it warns and ships the curated regions only. Those records and `dist/` are gitignored; never commit them.

Publish `dist/index.html` with the Artifact tool, passing `dist/files.json` as `files` (with `root` set to this folder) and the capability `{mcp: {servers: [{server: "host:claude_browser", tools: ["preview_start", "navigate", "get_page_text"]}]}}`.

## Self-hosted copy

`node build-web.mjs` (after `node build.mjs`) turns `dist/` into `dist-web/`, an ordinary static site. It has a full HTML document, Leaflet and topojson-client served locally, and a `_headers` file with a strict Content Security Policy. Outside Claude the page sets `data-host="web"` and fetches Open-Meteo and OSRM directly, so every feature works in any browser. `web/deploy.mjs` and `.github/workflows/good-outside-web.yml` deploy it to your own Cloudflare account behind Cloudflare Access, and refuse to deploy unless Access protects the hostname. Setup and the security and privacy notes are in [web/README.md](web/README.md).

`wrangler` is pinned to 4.149.0, the newest release at least two weeks old. `npm audit` reports advisories in its local-development simulator (miniflare's undici). Deploying doesn't use that simulator; it only talks to the Cloudflare API.

## How it differs from the hosted planner

Artifact pages run in a locked frame: no fetch to other hosts, no remote images or tiles, no geolocation, no server code.

- **Shared logic, unchanged.** `engine.mjs`, `trips.mjs`, `services.mjs` and the curated catalogs are copied byte-for-byte from `../public` at build time. `src/app.mjs` is a fork of `../public/app.mjs` for this runtime.
- **Regions.** The 49 curated regions bundled with the planner, plus provider records from the pinned snapshot release (`src/catalog-tiles.mjs`). The build keeps records whose source status is operating or unknown (no indoor or buildering areas) and splits them into 10° tiles under `data/catalog/` (124 tiles, 43,346 records for the 2026-10-23 release: OpenBeta 35,568, OpenSkiData 5,823, RIDB 1,955); a search loads only the tiles within 450 km. OpenBeta areas are grouped under their fourth path level (third where the path is shorter) and placed at the members' median, so a crag shows once rather than as each wall. Candidates for the activity within 450 km are spread across 0–100, 100–250 and 250+ km, up to 8 each and 24 in all. Within a band, curated regions come first, then OpenBeta areas by climb count, with named RIDB forests, parks, wilderness and recreation areas ahead of dams, harbors and visitor centers; distance breaks ties, and slots a band cannot fill go to the next-nearest areas. Provider points are source locations, not verified trailheads or access points, and the sheet says so. Biking and Bikepacking match the same areas. One RIDB name with a broken character is repaired at build time (`cleanName`). OpenSkiData is ODbL: the coverage panel carries its notice, and the tiles stay under ODbL. The 44,692-record D1 database itself is not included.
- **List.** One list instead of under-2-hour and 2–4-hour tabs: best weather first, then shortest drive. Areas over four hours are left out.
- **Drive times.** `src/drive.mjs`: OSRM road distance (one table request with `annotations=distance`) at a flat 60 mph average, as if on major highways the whole way. Where road distance is unavailable, straight-line distance × 1.3 stands in and the list marks it "est.", so every area has a time. An offline graph from Natural Earth roads was tried and rejected: its generalised network has gaps (US-101 near Olympia) that produced multi-hour detours.
- **Elevation bands.** At build time `src/bands.mjs` samples terrain within 10 miles of each curated region (from the hillshade's elevation tiles). Where at least 8% lies on each side of 3,000 ft (19 of 49 regions), the detail sheet fetches two forecasts at representative points near each band's median elevation, passing Open-Meteo's `elevation` parameter, and ranks each with `evaluate()`. Other areas note their terrain range.
- **Dates.** Trips start within the next 14 days. Forecast requests ask for exactly the trip's dates.
- **Rain before climbing.** `src/conditions.mjs` sums precipitation in the 48 hours before 8 am on the first day. It uses hourly values, or the two days' totals when only daily values are loaded. Climbing ratings note 1 mm or more, turn Excellent into Passable from 5 mm, and turn anything into Poor from 20 mm (`wetRock`). In Claude, climbing requests start two days before the trip. The list, detail sheet, top picks (`pickTop`, a copy of the shared `topPicks` using these ratings) and map all use it. Claude's phone mode loads no past days, so it's skipped there.
- **Ski snow surface.** `snowBefore()` reads the 72 hours before 8 am on the first day at the forecast point (an area's mapped point, usually near the base). It collects new snow, rain on snow (precipitation in hours above +1 °C, or daily totals beyond the snow's water), melt–freeze (a day above +3 °C and below −2 °C), no overnight freeze, the week's snowfall when loaded, and Open-Meteo's `snow_depth` on the first morning. `skiConditions()` turns Excellent into Passable for rain of 5 mm or more, melt–freeze or no freeze, unless 5 cm or more of new snow covers it. Model depth is one coarse value per mountain: the `elevation` parameter changes temperatures but not depth, and Whistler's village, Roundhouse and a point 7 km away all read the same. So depth under 10 cm only caps a rating at Passable. The self-hosted copy loads 7 days before for the areas (3 for the map) and always includes `snow_depth`. Claude loads 3 days before when skiing.
- **Freezing level.** Area forecasts include hourly `freezing_level_height`. Day rows show its range over the rated hours. A note gives the snow level, about 1,000 ft below it, on days with precipitation, and each by-elevation forecast says rain, mix or snow at its sample's elevation.
- **Self-hosted requests.** Outside Claude, forecast requests ask for `past_days=2&forecast_days=16` with every hourly field any setting uses, so changing dates, camping or activity re-rates instantly. The map's request leaves out the daily block (5 variables instead of 11); `fullDays()` rebuilds whole days from the hourly values. Grid points with no land within a grid step are skipped (`pointsNearLand`, from a 1:50m land mask), for example 213 of 256 around Victoria. Answers are kept in Cache Storage: forecasts for 15 minutes, the map's for 30, drive distances and geocoding for a day. So a page reload or repeat search makes no requests, and stale entries are pruned once per visit. Open-Meteo counts each location as a call, plus a fraction for over 14 days or over 10 variables. A new search costs roughly 300 calls against the free tier's 600 a minute and 10,000 a day per address. Refusals show Open-Meteo's own `reason`, such as the minutely or daily limit. The map loads in pieces of up to 50 points, so one failed piece leaves the rest drawn. Connection failures, timeouts and server errors get one retry after 1.5 s: near Victoria, BC, Open-Meteo once took 24 s to answer, likely while loading Canada's model data. Errors name the host and the browser's own error text.
- **Rating window.** Day trips (no camping night) are rated on 8 am–6 pm: `src/daytime.mjs` rebuilds the daily values the engine reads from hourly data (temperatures at 08:00–18:00; precipitation, probability, gusts and snowfall stamped 09:00–18:00, since Open-Meteo stamps accumulations at the end of their hour), so `evaluate()` and its thresholds are unchanged. Overnight trips keep full days plus the nights between them.
- **Surfing.** `src/coastline.mjs` derives open-coast points at build time: every 20 km along Natural Earth coastline arcs (arcs used by one country), facing the sea per ring winding, kept where open water reaches 150 km in most seaward directions (tested against the world terrain layer), named after the nearest GeoNames town. About 10,500 points worldwide in `data/coast.json`. Searching with Surfing takes the 40 nearest within 450 km, fetches Open-Meteo Marine (swell, period, direction, water temperature, sea level) 8 km offshore and wind at the shore, and rates each with `src/surf.mjs`: every daylight hour on size, period, swell direction against the shore and wind; a day is its best three-hour session, a trip its worst day. The map colours the coastline instead of the inland weather surface; the list keeps one point per town.
- **Closures.** The detail sheet's camping-and-access section is replaced by a closures link (`src/notices.mjs`): Forest Service forest alerts pages and NPS current-conditions pages are derived from each region's recorded links, with the recorded page offered beside them; other managers' own park pages are linked directly. The derived addresses follow those agencies' site-wide paths but were not loaded during the build.
- **Weather, drive times, postcodes.** `src/bridge.mjs` gives `createRegionClient` a transport that loads the Open-Meteo and OSRM JSON URLs in the Claude desktop app's built-in browser (`host:claude_browser`) and parses the page text. One tab, serialized requests, three allowlisted hosts. Each answer is checked against its request so a page still showing the previous response is re-read, forecasts request only the days the trip needs, and multi-point forecasts are chunked (and halved again if the page text comes back cut off). Live data loads only on ↻ Load, plus the detail sheet's "Explore a 10-mile radius" and forecasts by elevation. Opening the page, searching a place, opening a saved trip and zooming in only show what's loaded (`applySettings`). Zoomed in close, ↻ loads the nine samples around the map's centre. Changing activity, dates or camping re-rates the forecasts and drive times already loaded for that starting point (kept per area id). Whatever they don't cover stays unknown, and ↻ turns yellow until it's loaded. Host servers answer only for the artifact's owner, inside the Claude desktop app; everywhere else forecasts and drive times stay unknown and the page says why.
- **Weather map.** After a search the map shows no per-area markers. Instead `src/gradient.mjs` ranks a grid of forecast points across 600 km around the origin, 8×8 (about 86 km apart) in Claude and 16×16 (about 40 km apart) in the self-hosted copy, with the planner's `evaluate()` and paints a red–yellow–green surface, interpolated between ranked points only, feathered at the edges and clipped to land. Grid forecasts use their own client (`mapClient`) and leave out the freezing level. Activity and date changes repaint from what's loaded.
- **Map.** Leaflet over geography shipped with the page: Natural Earth countries, rivers, lakes, major highways with route plates, mountain-range names, peaks and 61 US National Park Service unit boundaries (public domain; layers pinned by commit and SHA-256 in `data-sources.json`), US Census interior state borders (via `us-atlas`), and GeoNames labels for cities of 100,000+ (CC BY 4.0, via `all-the-cities`). Coastlines and borders are drawn once from topology meshes. Light hillshade is rendered at build time (`src/hillshade.mjs`) from AWS Terrain Tiles (Tilezen; tiles pinned by SHA-256 in `terrain-tiles.json`): a zoom-4 world layer plus zoom-7 layers around each cluster of curated regions, multiplied over land and the weather surface. Labels avoid each other and the planner's markers. No national forests, wilderness, state or non-US parks, minor roads or trails.
- **Location snapshot.** Each area's details open with a small map of its surroundings (the same offline basemap, sharing the main map's loaded files) at zoom 9: the area, the drive destination where a curated region's gateway sits more than 2 km away, and the starting point. The closest towns of 2,000+ (GeoNames) are labelled first, then the largest in view. Under it, `src/locate.mjs` places the area in words: straight-line distance and direction from the starting point, the nearest town of 5,000+ within 60 km, a much closer small place when there is one, and a city of 50,000+ within 40 km when the town is small. Coordinates link to OpenStreetMap and Google Maps.
- **Live-data log.** Each request through the bridge or the background task is summarised (service, points, time, error code and the first 160 characters of an unreadable page) in a `diagnostics` document in the viewer's private storage (`data/users/<id>`), last 60 entries. Claude can read it with `ArtifactData` as the owner to see why forecasts failed on a device it cannot reach. Without the built-in browser, a search or ↻ may start the forecast task, which fetches up to 30 areas with the current activity's first; earlier saved fetches for the same origin are all reused.
- **Origin search.** Offline over GeoNames places with 1,000+ residents; falls back to Open-Meteo geocoding through the bridge for postcodes.
- **Not included.** Device location, the `/locations` directory, `/api/health`, MCP refresh tools and the ODbL export file.

The bridge relies on the documented `url`/`tabId` arguments and reads results defensively, but it has not yet been exercised against the real built-in browser.
